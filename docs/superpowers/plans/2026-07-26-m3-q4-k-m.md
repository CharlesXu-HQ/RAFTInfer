# M3 Q4_K_M Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run Qwen3.5-9B Q4_K_M GGUF end to end with exact greedy-token parity and meet the independent Q4_K_M llama.cpp performance gate.

**Architecture:** Treat Q4_K_M as a file-level mixed quantization recipe, not a single tensor dtype. Add exact GGUF block validation and independent CPU dequantization for the tensor types present in the pinned acceptance model, keep packed weights resident on the GPU, and dispatch separate decode matvec and prefill matmul kernels. Reuse a compatible bw24 kernel directly when its format and equations match; otherwise retain its scheduling technique without mislabeling NVFP4 or Q4_0 code as Q4_K.

**Tech Stack:** C++20, CUDA 13, BF16/FP32 accumulation, GGUF v3, RAFT 26.06, RMM 26.06, Rust 2024, CMake/Ninja, CTest, Bash.

## Global Constraints

- Q4_K_M is compared only with llama.cpp using the identical Q4_K_M GGUF.
- The acceptance GGUF revision, converter revision, command, size, and SHA-256 are pinned.
- The acceptance tensor-type inventory is captured before CUDA upload.
- Q4_K and Q6_K packed layouts are never interpreted through Q4_0 or NVFP4 kernels.
- Every CUDA unpacking path is compared with an independent CPU implementation that shares no bit-extraction helper.
- Exact greedy-token equality is required for four prompts and 32 generated tokens per prompt.
- Q4_K_M release gates are PP128 `>=1.0x`, PP512 `>=1.0x`, and TG128 after PP512 `>=1.0x`, with at least one metric `>=1.1x`.
- Imported source retains its upstream commit, license, original path, and modification record.
- RAFT/RMM own streams, allocations, and workspaces; no second runtime is introduced.
- No full-model BF16 dequantized weight copy may remain resident after model loading.
- Execute the M4 BF16 performance plan before integrating this plan into the
  final executor, so Q4_K_M does not conceal shared attention, graph, cache, or
  launch bottlenecks.

- [ ] **Step 1: Add byte-literal golden blocks**

Use fixed block bytes and expected FP32 values generated once with the pinned
llama.cpp reference utility. Store the bytes and expected floats directly in
the test source so the CPU reference does not call llama.cpp at test time.
Cover positive/negative scales, nonzero minima, low/high nibbles, Q6 high bits,
and zero blocks.

- [ ] **Step 2: Verify RED**

Expected: missing reference functions.

- [ ] **Step 3: Implement Q4_K decoding independently**

Interpret the block as:

```text
bytes 0..1   : FP16 d
bytes 2..3   : FP16 dmin
bytes 4..15  : packed 6-bit scale/min fields
bytes 16..143: 256 4-bit quants
```

Decode scale/min fields with local masks and shifts, then compute each group
using the pinned GGML Q4_K equation:

```cpp
output[index] = d * scale[group] * quant -
                dmin * minimum[group];
```

- [ ] **Step 4: Implement Q6_K decoding independently**

Combine the low four bits and packed high two bits into signed six-bit values,
apply the signed per-16-element scale and block FP16 multiplier, and write FP32.

- [ ] **Step 5: Run host reference tests**

Run the focused test and complete `scripts/local-check.sh`. Expected: golden and
random-block comparisons pass exactly within the reference tolerance.
